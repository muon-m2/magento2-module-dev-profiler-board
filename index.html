Companion to Muon_DevProfiler · developer mode only

The same runs, without leaving the browser

A web board for captured profiler runs: a ledger that updates as new requests land, a cache verdict with the block that caused it, SQL shapes ranked by finding, the fallback ladder, and a diff between any two runs. It renders its own document and resolves nothing through the theme — so the storefront cannot restyle it, and it cannot pollute the evidence it displays.

OSL-3.0 Magento 2.4.9 PHP 8.3 – 8.5 no theme dependency no static deploy

Five panels and a ledger

Each answers one question, and says when it cannot.

Overview

Request, context and the verdict banner — method, URL, store, theme, duration, peak memory.

Fallback

The resolution ladder per file: which directory won, which copies lost, and an explicit note when the replay could not be trusted.

SQL

Statement shapes with execution counts, timings and calling file:line, ranked by finding rather than by order of appearance.

Layout

Handles in play, blocks declaring cacheable="false", and constructor opt-outs — separating what was declared from what was actually generated.

Raw

The stored document verbatim, plus JSON and Markdown exports for pasting into an issue.

Compare

Two runs side by side: what changed in the verdict, the timings and the statement set.

The verdict vocabulary

Delegated to the collector, so the board and bin/magento muon:profile:show can never disagree about the same token.

hit miss uncacheable n/a

Install

Both repositories are public; no authentication.

# the collector, then the board
composer config repositories.muon-dev-profiler vcs \
    https://github.com/muon-m2/magento2-module-dev-profiler
composer config repositories.muon-dev-profiler-board vcs \
    https://github.com/muon-m2/magento2-module-dev-profiler-board
composer require --dev muon/module-dev-profiler-board

bin/magento module:enable Muon_DevProfiler Muon_DevProfilerBoard
bin/magento setup:upgrade

Then open /muon_profiler/ on the storefront.

Access

The board is served only in developer mode. That gate is the collector's own, delegated rather than re-tested — two answers to "is profiling active here" would eventually disagree, and the wrong disagreement is a board that renders on an installation the collectors have correctly decided is production. It fails closed: an installation that cannot report its own mode is treated as production. In any other mode every route returns 404.

Deployment mode is the only access control — there is no ACL, admin-session check or IP allowlist behind it. On a shared or public host, make sure the web tier's MAGE_MODE is what you think it is: it comes from the FastCGI environment and can differ from what bin/magento deploy:mode:show reports for the CLI.

Why it looks nothing like your storefront

The board builds its own HTML document and serves its own CSS and JS through its own routes. No block, no .phtml, no layout handle, no view file, and nothing through setup:static-content:deploy.

That is not an aesthetic choice. This module displays theme-fallback evidence, and a board that resolved its own template through the fallback chain would add its own resolutions to the very list the reader is trying to interpret. Its requests are also excluded from the collector's ring, so browsing the board — and the poll behind it — cannot evict the runs being inspected.

It needs the collector

Muon_DevProfiler

The headless profiler that records the runs: theme-fallback forensics, cache verdicts, layout opt-outs and SQL shapes, captured per request and readable from the CLI. The board is a reader; this is what does the recording.
